### Week 2 · Day 3
1. Agent Loop 的本质：一个 while 循环 + 三条消息协议——现代 Agent 框架（Codex、OpenClaw 等）的循环骨架和这个没有本质区别，只是多了流式、多工具、记忆管理

4. 状态外置：Agent 不持有历史，run(messages) 纯粹是"处理这段对话"
现在agent类调用逻辑
外部调用 agent.run(messages)
    → 进入run()，进入while True循环
        → llm.chat拿到模型回复
        → 如果无tool_calls → return message → 回到外部代码，任务结束（message只返回最后一次回答，完整对话在messages列表）
        → 如果有tool_calls，进入for循环
            → result = self.execute_tool_call(tool_call)
                → 进入execute_tool_call
                    → 找到工具执行 return tool(**args)
                ← 回到run，赋值给result
            → append工具结果到messages
    → 回到while循环开头，再次调用llm.chat，新一轮思考

### Week 5 · Day 1
初步学习mcp，手写接口了解底层
- .stdin stdout：标准输入输出流 print input就是包装的stdin stdout
- for line in sys.stdin stdin是文本流，可迭代，遇到换行符截断，没有新数据就*阻塞等待*
- flush=True：不缓存，立即输出（默认有缓存区，消息满了才输出）
- 进程（运行中的程序）每个进程会被操作系统给与一个pid数字，用于识别，运行结束就收回
- 进程有输入端输出端（std） eg：input print函数，把输入端链接键盘，输出端链接终端

- process = subprocess.Popen(
    [sys.executable, str(server_path)],
    stdin=subprocess.PIPE,
    stdout=subprocess.PIPE,
    text=True,
    encoding="utf-8",
)
链接两个进程，操作系统创造两个*单向*管道1和2 
[sys.executable, str(server_path)]-> 启动子进程，靠pid识别->print(process.pid)
管道 1：父 → 子（对应参数 stdin=subprocess.PIPE）
作用：父发 JSON 消息给子进程
当写 stdin=subprocess.PIPE：
subprocess 创建管道 1
管道 1【读端】，绑定到子进程的 sys.stdin
✅ 子进程这边：直接 for line in sys.stdin: 循环读取。
子根本不知道管道存在，对子来说，就像读取控制台输入。
管道 1【写端】交给父进程，包装成 process.stdin
✅ 父进程这边：只能用 process.stdin.write(内容) 写数据，写完要flush()推送。
❗父自己的sys.stdin是父的控制台，和这个管道无关。
流向：
父 process.stdin.write() → 管道内核缓冲区 → 子 sys.stdin（for line 读取）
管道 2：子 → 父（对应参数 stdout=subprocess.PIPE）
作用：子返回 JSON 结果给父进程
当写 stdout=subprocess.PIPE：
subprocess 创建管道 2
管道 2【写端】，绑定到子进程的 sys.stdout
✅ 子进程这边：直接print(xxx, flush=True)，print 默认输出到sys.stdout，自动写入管道。
子不用操作管道对象，就像打印到屏幕。
管道 2【读端】交给父进程，包装成 process.stdout
✅ 父进程这边：process.stdout.readline() 阻塞读取一行返回结果
❗父自己的sys.stdout就是终端屏幕，和这个管道无关。
流向：
子 print() → 子的 sys.stdout → 管道内核缓冲区 → 父 process.stdout.readline()
子进程的sys.stdin、sys.stdout在启动瞬间就被重定向，接到管道两端。
所以子代码：for line in sys.stdin:        # 读管道1读端
    ...
    print(result, flush=True) # 写管道2写端
👉 子只操作自带的sys标准流，看不到管道对象，代码和普通读控制台程序一模一样。
父进程
父进程自己的 sys.stdin/sys.stdout 完全没变，仍然绑定终端屏幕，没有任何重定向。
管道剩下的两个端点，单独打包，放在process这个 Popen 实例里面：
• process.stdin：管道 1 写端（发消息给子）
• process.stdout：管道 2 读端（接收子返回）
父没有办法直接用sys去和子通信，必须手动操作这两个管道对象
